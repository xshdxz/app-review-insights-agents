# 可靠性：崩溃一致性与故障注入

**一句话**：进程被硬杀之后，同一次运行能不能用同一个 `run_id` 接着跑完，而且结果与
"一次跑完"**逐字节相同**？这套用例把答案变成可复现的证据，并且**零模型成本**。

复现命令（一条）：

```powershell
..venv\Scripts\python -m pytest -m reliability
```

---

## 为什么能做到零成本

分析流水线的模型调用走**回放**（`DEMO_MODE=replay` + `data/recordings/demo-replay.json`）。
回放没有网络往返，因此：

- 不需要密钥、不产生任何费用；
- 同一输入必然产出同一结果——这条本身是被测试守着的
  （`tests/reliability/test_baseline_determinism.py`：同一输入回放两遍，四张表的快照逐字节相同）。

第二条是关键：**只有确定性成立，"崩溃+续跑"才可能与"一次跑完"做逐字节比较**，
而不是只能比个大概。这把演示模式从"给访客看的降级形态"变成了可靠性工程的方法论基座。

## 为什么必须是真子进程

进程内注入异常会被 `except` / `finally` 接住，证明不了"检查点真的落盘了"。
所有场景都在**独立子进程**里真实死亡：

| 手法 | 怎么死 | 覆盖的是 |
|---|---|---|
| 确定性崩溃 | `ARI_CRASH_AFTER_STAGE`：指定阶段的检查点落盘后立刻 `os._exit(137)`，绕过全部 `finally` / `atexit` | 阶段边界、批次边界 |
| 随机时刻硬杀 | 父进程盯进度日志，等第 N 个检查点落盘后随机等一小段，再 `Popen.kill()`（Windows=`TerminateProcess`，POSIX=`SIGKILL`） | 阶段**内部**：模型调用途中、写事务途中 |

崩溃注入**不改生产代码**：在子进程内给 `RunRepository.save_output` 打一层包装即可。
生产路径因此零改动，这套基座可以随时摘掉而不影响任何行为。

## 场景矩阵

### 确定性崩溃点（10）

| 场景 ID | 崩溃时机 | 崩溃时应当已落盘的检查点 |
|---|---|---|
| `stage:collect` | 采集输出落盘后 | collect |
| `stage:clean` | 清洗输出落盘后 | collect, clean |
| `stage:analyze_batches` | 批次清单落盘后 | + analyze_batches(清单) |
| `stage:consolidate` | 跨批归并落盘后 | + analyze_batches(各批次) |
| `stage:audit_evidence` | 证据审计落盘后 | 同上 + consolidate |
| `stage:validate_findings` | 确定性校验落盘后 | 同上 + audit_evidence |
| `stage:plan` | 需求草拟落盘后 | 同上 + validate_findings |
| `stage:generate_tests` | 测试用例落盘后 | 同上 + plan |
| `stage:validate_traceability` | 追溯校验落盘后 | 同上 + generate_tests |
| `batch:0` | 第 0 批结果落盘后 | collect, clean, analyze_batches(清单+批次 0) |

### 随机时刻硬杀（5）

| 场景 ID | 触发点 |
|---|---|
| `kill:after-3-saves-50ms` | 第 3 个检查点后约 50ms |
| `kill:after-5-saves-50ms` | 第 5 个检查点后约 50ms |
| `kill:after-7-saves-60ms` | 第 7 个检查点后约 60ms |
| `kill:after-9-saves-60ms` | 第 9 个检查点后约 60ms |
| `kill:after-10-saves-50ms` | 第 10 个检查点后约 50ms |

随机硬杀额外注入了每次模型调用 120ms 的延迟（`ARI_REQUEST_DELAY_MS`）：回放没有网络往返，
整条流水线只要几百毫秒，"杀在调用途中"根本定不了时；不注入延迟，这一支会退化成空测。

## 每条用例断言什么

1. **崩溃确实生效**——进程以 137 退出，且没走到打印摘要那一步；否则后面所有断言都可能是在
   "没崩"的前提下成立的。
2. **负向**——崩溃点之后的阶段输出必须**不存在**。没有这一条，"续跑正确"可能只是因为根本没崩。
3. **原子性**——已落盘的每个阶段输出都能被对应的 Pydantic 模型校验（没有半截 JSON，
   schema 也没有在续跑中被拼歪）。
4. **收敛性**——续跑后的阶段输出与"一次跑完"的参照**逐字节相同**（只规范化 run_id 与时间戳）。
5. **不重复计费**——崩溃进程 + 续跑进程发出的模型请求总数 **等于**一次跑完的请求数，
   即"已完成的工作绝不被重做"。

随机硬杀那一支允许重做**被中断阶段**的调用（没落盘的结果不算已完成），因此它的口径是
"请求集合的并集等于基线集合、且续跑进程内部无重复"。这个差异是刻意的，不是放宽。

## 实测结果

| 项 | 实测值 |
|---|---|
| 用例数 | **21 项全绿**（10 个确定性崩溃点 + 5 个随机硬杀 + 2 个基线自检 + 2 个护栏自检 + 2 个文档一致性） |
| 一次跑完的模型请求数 | 13 次（1 批次 + 1 归并 + 1 审计 + 1 需求 + 9 用例） |
| 检查点落盘次数 | 12 次 |
| 套件耗时 | 约 120 秒（含子进程覆盖率收集）；默认不随主套件运行 |
| 模型费用 | **$0**（全部回放） |

## 反向验收：绿灯不是恒真的

一组永远为真的断言比没有断言更危险。因此这套基座自带三条反向验收：

- **A（已实测）**：把 `lease.can_resume` 换回"只接受 waiting/timed_out"的旧行为，
  抽查的崩溃用例**必须重新变红**。实测：3/3 变红，还原后 3/3 变绿。
- **B（已实测）**：崩溃注入未生效时（例如阶段名写错），`assert crashed.crashed` 必须失败，
  而不是让用例静默通过。实测：把阶段名换成不存在的值，子进程正常跑完（退出码 0、状态
  `completed`），该断言必然变红。
- **C（已实测）**：负向断言必须能抓到"崩溃点之后的输出存在"。它在开发过程中真的抓到过一次——
  当时的期望集合漏掉了 `analyze_batches` 的批次行，被它当场报为越界写入。

另外，随机硬杀那一支带**空洞守卫**：若子进程在被杀之前已经跑完，则断言
`result.summary is None` 与"库里状态仍是 running"会失败。开发中确实踩到过——
最初两个参数就是这样**假绿**的。

## 已知边界

这套用例证明的是**进程级故障**下的一致性。以下**没有**被证明，不要当成已覆盖：

- **掉电 / fsync 级数据安全**：随机时刻硬杀是对它的近似，不等于证明了掉电安全。
- **跨主机的接管判定**：租约靠 `host:pid:token` 判定持有者存活，跨主机时判不出来，
  退回心跳超时窗口（`Settings.lease_timeout_seconds`，下界 300 秒）。
- **PID 复用**：极端情况下新进程复用崩溃进程的 PID，会让接管**保守地拒绝**直到心跳过期。
  方向是安全的（不会出现两个执行者），但会延迟恢复。
- **多写者并发**：互斥依赖 SQLite 的 `BEGIN IMMEDIATE`；这条路径尚未在真实多进程竞争下压测。
