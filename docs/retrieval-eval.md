# 检索质量评测

> 这份文档回答一个问题：**RAG 那条线的检索到底好不好？** 在它存在之前，这个项目对检索只有实现、没有度量——
> 融合权重 0.6/0.4 与「查询改写能提升召回」这类说法，都没有任何数字支撑。
>
> 尺子造好之后，它当场量出并推动修掉了三个问题：中文长问句必然落空（D-17）、查询改写的负收益（D-18）、
> 「混合检索」其实只是重排器（D-19）——最后一个修完，才第一次量出向量那一路的真实收益（recall@5 0.595 → 0.714）。

## 怎么跑

```powershell
# 只校验查询集（零成本，CI 每次 push 都跑）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --validate-only

# 离线评测：纯 FTS5，不需要密钥
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --output output\\retrieval-eval.json

# 追加「查询改写」配置（需要模型密钥，只有显式加这个开关才会真实调用模型）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --live-rewrite

# 追加「混合检索」配置（需要向量 provider：EMBEDDING_API_KEY 或 EMBEDDING_LOCAL_MODEL_PATH）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --hybrid

# 门禁：低于阈值即非零退出（CI 用它守住不回归）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --fail-under-recall-at-3 0.5
```

**默认不带任何开关时，这个脚本一次外部调用都不发**（纯 FTS + 数据集校验）。两个可选配置互相独立、
都必须显式打开 —— 此前 `--live-rewrite` 只写在文档里、代码从未读过它，配了密钥就会悄悄产生模型调用
（D-20，已修）。

## 查询集与指标口径

查询集在 `evals/gold-retrieval.json`：21 条查询（中文 9 / 英文 12），**答案锚定既有黄金集的 `expected_review_ids`**，
不另造一套标注。查询写成「用户会怎么问」，而不是照抄评论原句——照抄的话词面检索必然命中，测不出任何东西。
语料直接用黄金集里的 120 条评论，索引建在**临时库**上，评测不碰 `data/` 下的真实档案。

| 指标 | 口径 |
|---|---|
| recall@k | 前 k 条里找回了多少比例的**期望项**（分母是期望项个数） |
| MRR | 第一条命中的排名的倒数——衡量「最相关的那条排得够不够靠前」 |
| precision@k | 前 k 条里有多少是期望项（分母是实际返回条数） |

指标实现只有一处（`src/app_review_insights/rag/metrics.py`），并配了边界单测（并列、k 大于结果数、期望为空、结果为空）。
**为什么值得单独存在**：这个项目已经栽过两次「指标本身错了」——D-10（打分取错字段，头条指标结构性恒为 0）与 D-11（用词面一致率冒充召回）。

## 首跑就撞出一个真实缺陷（D-17）

第一次跑评测，`q-data-loss` 那条查询与目标评论只差两个字（「我过去几个月」vs「过去三个月」）却召回 0。
把 `build_fts_query` 的输出 dump 出来，原因一目了然：

```
查询：更新之后我过去几个月的训练记录全没了
  AND: "更 新 之 后 我 过 去 几 个 月 的 训 练 记 录 全 没 了"
  OR : "更 新 之 后 我 过 去 几 个 月 的 训 练 记 录 全 没 了"   ← 两轮是同一个串
索引：更 新 之 后 过 去 三 个 月 的 训 练 记 录 全 没 了 。      ← 差「我」「几」两个字
```

**没有空白或标点的中文问句会变成一个「必须逐字相邻出现」的整段短语**，而「严格 AND → 无结果退化 OR」两级用的又是同一个串，
于是换个说法的中文问句两轮都命中不了，RAG 页面回答「当前语料中没有找到与该问题相关的评论」——**静默失败，还说了假话**。
（带全角标点时会被切成两段，所以偶有命中，这也解释了为什么它一直没被发现。）

修法：**宽松回退那一级**对 CJK 长段展开为**相邻二元组**（`更新 OR 新之 OR 之后 …`），保留「相邻」约束（`订阅` 仍不会命中订/阅分散的评论，
既有用例守着这一点），同时容忍局部改写；严格模式保持整段短语不变。详细记录见 `docs/defect-list.md` 的 D-17。

## 修复前后（同一查询集，离线配置）

| 指标 | 修复前 | 修复后 | 说明 |
|---|---:|---:|---|
| recall@1 | 0.333 | **0.429** | 第一条就给对的更多了 |
| recall@3 | 0.357 | **0.595** | 中文那半边拉动 |
| recall@5 | 0.357 | **0.595** | 与 @3 相同 ⇒ 缺的那些不是「排得靠后」，而是**根本没被召回** |
| MRR | 0.667 | **0.873** | 命中的位置整体前移 |
| precision@5 | 0.333 | 0.319 | 略降：宽松兜底会带回少量弱相关评论——**这个代价如实列在这里** |
| recall@3（英文） | 0.500 | 0.500 | 英文路径未改动，**无回归**（这也是改动安全性的证据） |
| recall@3（中文） | 0.167 | **0.722** | 4.3 倍 |

## 查询改写：先证明它是负收益，再把它关进「零结果才触发」的闸里（D-18）

同一天、同一查询集，跑了一次带改写的配置（`--live-rewrite`，21 次改写调用，不足 1 分钱）。
**无条件改写**（旧策略）的结果是全面下降：

| 指标 | 纯 FTS（基线） | + 无条件改写 | + 改写（只在零结果时触发，现行） |
|---|---:|---:|---:|
| recall@1 | **0.429** | 0.357 | 0.429 |
| recall@3 | **0.595** | 0.524 | 0.595 |
| recall@5 | **0.595** | 0.548 | 0.595 |
| MRR | **0.873** | 0.746 | 0.873 |
| precision@5 | **0.319** | 0.256 | 0.319 |
| recall@3（英文） | **0.500** | 0.417 | 0.500 |
| recall@3（中文） | **0.722** | 0.667 | 0.722 |

**全面下降。** README 此前写着「Query Rewriting Agent…提升召回率」——那句话被自己的数据推翻了。

根因不在改写本身，而在**合并那一步跨查询比较分数**：`RagAnswerer` 把多条改写查询的结果按归一化分数合并排序，
而每条查询的 top1 都被 min-max 归一化成 1.0，于是改写出来的短查询（更泛、更容易命中泛化评论）的头部结果
会把原查询的精确结果挤下去。**分数跨查询不可比**，这才是问题。

修法取了候选三条里最保守的一条 —— **③ 只在原查询零结果时才启用改写**，并把策略收敛到**唯一入口**
`rag/answer.gather_evidence`（UI 与评测脚本共用同一个函数；脚本不再另抄一份合并逻辑，否则一边改了另一边
没跟上，数字就会说谎）。两条结构性保证：

1. **命中即止**：原查询有结果就完全不碰改写 ⇒ 负收益在**结构上**不可能发生，不是调参调出来的。
2. **回退路按名次轮转**（rank round-robin，不跨查询比分数）—— 这是上面那个根因的直接修法。

复测结果里 `rewrite_triggered = 0`：**21 条查询没有一条触发改写**，因为 D-17 修好之后纯 FTS 对每条查询都
至少返回一条结果；改写那一列的每个数字都与纯 FTS 逐位相同。所以：

- **负收益确实消失了，而且是结构性的**——不是「这批评测刚好没亏」，而是「没有触发就没有跨查询比较」。
- **改写的召回收益仍然没有被量到**——在这批查询上它一次都没上场。它能不能救回「纯 FTS 零结果」的问句，
  由一条端到端用例守着（真实 FTS、原查询零结果、改写把证据救回来）；而「命中了但排得不够好」这种场合
  要不要让改写上场，需要**按名次融合（RRF）+ 原查询优先**，那是下一个可度量的改动，**本次不做**。

## 混合检索：从「重排器」改成「两路召回」（D-19）

补向量那一路的数字之前，先读了代码——发现了一件更根本的事：

```python
# 修复前（retrieval.py::_rank）
by_id = {hit["review_id"]: score for hit in hits}
for chunk in chunks:  # ← 只遍历 FTS 已召回的候选
    chunk.score = 0.6 * chunk.score + 0.4 * by_id.get(chunk.review_id, 0.0)
```

**向量那一路找到的评论根本没有机会进入结果**——它只能改动 FTS 命中的顺序，
也就是说这个「混合检索」**结构上不可能提升召回**，与 README 的表述所暗示的能力不符。
（`search_embeddings` 其实已经返回了 `content/app_id/platform`，构造候选所需的数据全在手上，只是没用。）

已改成**两路召回**：向量那一路的候选（先过平台过滤，社交语料不能从侧门溜进来）并入候选集，
FTS 分为 0、靠向量分竞争；融合权重与截断逻辑不变。两项测试钉住它：只有向量能找到的评论必须进入结果、
向量补进来的候选同样受平台隔离约束。

修完之后才谈得上量。本机没有 embedding 服务（DeepSeek 不提供 `/embeddings`，实测 404），于是装了
`sentence-transformers`（现在是可选 extra `[embeddings]`），用**本地模型** `BAAI/bge-small-zh-v1.5`（512 维、中文向）跑。
下面这条是不带向量那一路的基线；把 `EMBEDDING_ENABLED=true` 与
`EMBEDDING_LOCAL_MODEL_PATH=BAAI/bge-small-zh-v1.5` 设进环境后，同一条命令就会多出一个 `hybrid` 配置：

```powershell
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --hybrid --output output\\retrieval-hybrid.json
```

| 指标 | 纯 FTS（基线） | 混合（两路召回 + bge-small-zh） | 差值 |
|---|---:|---:|---:|
| recall@1 | 0.429 | 0.429 | 0 |
| recall@3 | 0.595 | **0.619** | +0.024 |
| recall@5 | 0.595 | **0.714** | **+0.119** |
| MRR | 0.873 | **0.885** | +0.012 |
| precision@5 | **0.319** | 0.286 | −0.033 |
| recall@3（英文） | 0.500 | **0.542** | +0.042 |
| recall@3（中文） | 0.722 | 0.722 | 0 |

**逐条看比看均值更有信息**：21 条查询里 **4 条改善、0 条变差、17 条持平**（按 recall@5 计）：

| 查询 | 语言 | recall@5 |
|---|---|---:|
| `q-localization` | zh | 0.00 → **1.00** |
| `q-trial-billing` | en | 0.50 → **1.00** |
| `q-update` | en | 0.50 → **1.00** |
| `q-price-clarity` | zh | 0.50 → **1.00** |

`q-localization` 属于纯 FTS **一条都没召回**的那类问题——向量那一路把它整条捞了回来，这正是两路召回的意义。

**两点不能省**：

1. **多数收益落在第 4–5 名**：recall@3 只多 1 个期望项，recall@5 多 5 个。原因是 FTS 那一路带着 0.6 的权重、
   稳稳占住前排，向量补进来的候选通常只拿 0.4×余弦分。**0.6/0.4 是拍的，从没调过**——往向量侧挪一挪很可能
   把这几个候选提前，那是下一个可度量的改动（本次不做）。
2. **样本只有 21 条查询**：recall@3 的 +0.024 恰好是「一条查询里一个期望项」的量级，属于**有信号但不显著**。
   站得住的结论是「**零回归 + recall@5 明显变好**」，不是「recall@3 提升了」。

代价如实列出来：precision@5 从 0.319 降到 0.286——两路召回必然带回更多弱相关评论，这是**召回换精度**的常规取舍。

## 没测的部分（如实列出，不假装）

- **向量 / 混合检索的质量**：本机没有 embedding provider（DeepSeek 不提供 `/embeddings`；没有本地向量运行时；HF 缓存里只有 reranker）。
  接线已经做完并测过（`--hybrid` + 两路召回，见上一节），但**没有数字**。
  这也意味着 0.6/0.4 的融合权重至今没被验证过——它是**未测**，不是「已经比过所以没问题」。
- **跨语言检索**（中文提问、英文语料）：词面检索天然做不到，那正是向量那一路的职责；本评测用 language 分组把差距显式暴露出来，
  而不是把中英混在一起做一个平均数把它盖住。
- **多 App 合并语义**（`search_many` 的每个 App 取 top）：需要多 App 语料才谈得上，本次语料只有一个 App，属范围之外。
- **改写兜底的收益**：现行策略下改写只在「原查询零结果」时上场，而这 21 条查询**没有一条触发它**
  （`rewrite_triggered = 0`），因此「改写能多召回多少」在数字上仍是空白。不被触发的直接证据是纯 FTS 对每条
  查询都至少返回一条结果；兜底路径本身由端到端用例守着，但**它的上界没有被量过**。
- **答案质量**：本次只看检索。答案写得好不好是生成侧的事，需要另一套评测。

## CI 门禁

`.github/workflows/ci.yml` 的 test job 里跑 `--validate-only` 与离线评测，阈值 `recall@3 >= 0.5`（当前 0.595，留了余量）。
它守的是「检索不回归」，不是「检索足够好」。混合检索那一路**不进 CI**：它要一个 2GB 级的本地模型，
  在 CI 里下载既慢又脆。它的数字用上面那条命令本地复现，结论与代价都写在文档里。
