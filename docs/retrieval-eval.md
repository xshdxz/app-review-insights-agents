# 检索质量评测

> 这份文档回答一个问题：**RAG 那条线的检索到底好不好？** 在它存在之前，这个项目对检索只有实现、没有度量——
> 融合权重 0.6/0.4 与「查询改写能提升召回」这类说法，都没有任何数字支撑。

## 怎么跑

```powershell
# 只校验查询集（零成本，CI 每次 push 都跑）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --validate-only

# 离线评测：纯 FTS5，不需要密钥
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --output output\\retrieval-eval.json

# 追加「查询改写」配置（需要模型密钥，不足 1 分钱/次）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --live-rewrite

# 门禁：低于阈值即非零退出（CI 用它守住不回归）
.\\.venv\\Scripts\\python scripts/run_retrieval_eval.py --fail-under-recall-at-3 0.5
```

## 查询集与指标口径

查询集在 `evals/gold-retrieval.json`：21 条查询（中文 9 / 英文 12），**答案锚定既有黄金集的 `expected_review_ids`**，
不另造一套标注。查询写成「用户会怎么问」，而不是照抄评论原句——照抄的话词面检索必然命中，测不出任何东西。
语料直接用黄金集里的 120 条评论，索引建在**临时库**上，评测不碰 `data/` 下的真实档案。

| 指标 | 口径 |
|---|---|
| recall@k | 前 k 条里找回了多少比例的**期望项**（分母是期望项个数） |
| MRR | 第一条命中的排名的倒数——衡量「最相关的那条排得够不够靠前」 |
| precision@k | 前 k 条里有多少是期望项（分母是实际返回条数） |

指标实现只有一处（`src/app_review_insights/rag/metrics.py`），并配了边界单测（并列、k 大于结果数、期望为空、结果为空）。
**为什么值得单独存在**：这个项目已经栽过两次「指标本身错了」——D-10（打分取错字段，头条指标结构性恒为 0）与 D-11（用词面一致率冒充召回）。

## 首跑就撞出一个真实缺陷（D-17）

第一次跑评测，`q-data-loss` 那条查询与目标评论只差两个字（「我过去几个月」vs「过去三个月」）却召回 0。
把 `build_fts_query` 的输出 dump 出来，原因一目了然：

```
查询：更新之后我过去几个月的训练记录全没了
  AND: "更 新 之 后 我 过 去 几 个 月 的 训 练 记 录 全 没 了"
  OR : "更 新 之 后 我 过 去 几 个 月 的 训 练 记 录 全 没 了"   ← 两轮是同一个串
索引：更 新 之 后 过 去 三 个 月 的 训 练 记 录 全 没 了 。      ← 差「我」「几」两个字
```

**没有空白或标点的中文问句会变成一个「必须逐字相邻出现」的整段短语**，而「严格 AND → 无结果退化 OR」两级用的又是同一个串，
于是换个说法的中文问句两轮都命中不了，RAG 页面回答「当前语料中没有找到与该问题相关的评论」——**静默失败，还说了假话**。
（带全角标点时会被切成两段，所以偶有命中，这也解释了为什么它一直没被发现。）

修法：**宽松回退那一级**对 CJK 长段展开为**相邻二元组**（`更新 OR 新之 OR 之后 …`），保留「相邻」约束（`订阅` 仍不会命中订/阅分散的评论，
既有用例守着这一点），同时容忍局部改写；严格模式保持整段短语不变。详细记录见 `docs/defect-list.md` 的 D-17。

| 指标 | 修复前 | 修复后 | 说明 |
|---|---:|---:|---|
| recall@1 | 0.333 | **0.429** | 第一条就给对的更多了 |
| recall@3 | 0.357 | **0.595** | 中文那半边拉动 |
| recall@5 | 0.357 | **0.595** | 与 @3 相同 ⇒ 缺的那些不是「排得靠后」，而是**根本没被召回** |

## 查询改写：数据说它是负收益（D-18）

同一天、同一查询集，追加跑了一次带改写的配置（`--live-rewrite`，21 次改写调用，不足 1 分钱）：

| 指标 | 纯 FTS（基线） | + 查询改写 |
|---|---:|---:|
| recall@1 | **0.429** | 0.357 |
| recall@3 | **0.595** | 0.524 |
| recall@5 | **0.595** | 0.548 |
| MRR | **0.873** | 0.746 |
| precision@5 | **0.319** | 0.256 |
| recall@3（英文） | **0.500** | 0.417 |
| recall@3（中文） | **0.722** | 0.667 |

**全面下降。** README 此前写着「Query Rewriting Agent…提升召回率」——那句话被自己的数据推翻了，已改。

最可能的原因在合并那一步：`RagAnswerer` 把多条改写查询的结果**按归一化分数**合并排序，而每条查询的 top1 都被
min-max 归一化成 1.0，于是改写出来的短查询（更泛、更容易命中泛化评论）的头部结果会把原查询的精确结果挤下去。
换句话说：**问题不在改写本身，而在「跨查询比较分数」这个做法**。

候选修法（**本次不做**，属检索算法改动，超出「只度量」的范围）：① 改用 RRF（按名次融合，天然可比）；
② 原查询的结果优先、改写只用于补召回；③ 只在严格检索无结果时才启用改写。三条都得用同一套评测来验，
否则就是又一次「凭感觉改检索」。

## 没测的部分（如实列出，不假装）

- **向量 / 混合检索**：本机 `EMBEDDING_ENABLED=false` 且没有 embedding provider，所以那一路**未测**。
  评测脚本支持注入 embedding store，配好 provider 后可以直接跑，但**现在没有数字**。
  这也意味着 0.6/0.4 的融合权重至今没被验证过——它在本次评测范围之外，不是「已经比过所以没问题」。
- **跨语言检索**（中文提问、英文语料）：词面检索天然做不到，那正是向量那一路的职责；本评测用 language 分组把差距显式暴露出来，
  而不是把中英混在一起做一个平均数把它盖住。
- **多 App 合并语义**（`search_many` 的每个 App 取 top）：需要多 App 语料才谈得上，本次语料只有一个 App，属范围之外。
- **答案质量**：本次只看检索。答案写得好不好是生成侧的事，需要另一套评测。

## CI 门禁

`.github/workflows/ci.yml` 的 test job 里跑 `--validate-only` 与离线评测，阈值 `recall@3 >= 0.5`（当前 0.595，留了余量）。
它守的是「检索不回归」，不是「检索足够好」——后者要等向量那一路有数字之后才谈得上。
