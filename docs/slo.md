# SLI / SLO 与错误预算

> **本文的目标不是"写出漂亮的数字"，而是让每个数字都可算。** 每个 SLI 都给出确切的
> 计算方式与数据来源；拿不到数据的指标不写进来。标着「初始值」的目标是待校准的起点，
> 不是拍脑袋的承诺——跑够一周真实数据后按实测分布收紧或放宽。

## SLI 定义

| # | SLI | 定义 | 怎么算 | 数据来源 |
|---|---|---|---|---|
| 1 | 进程可用性 | **常驻进程**（worker）能抓到指标的时间比例 | `avg_over_time(up{job=~"ari-.*"}[1d])` | `/metrics` |
| 2 | 就绪状态 | worker 调度器就绪 | `ari_worker_ready` | `/metrics` |
| 3 | 阶段耗时 | 每个流水线阶段的耗时分布 | `ari_stage_duration_seconds{stage=...,quantile="0.95"}` | `/metrics`（源：`stage_timings` 表） |
| 4 | 模型调用耗时 | 每个阶段的模型调用耗时分布 | `ari_model_latency_seconds{stage=...,quantile="0.95"}` | `/metrics`（源：`model_usage` 表） |
| 5 | 任务成功率 | 监控任务成功比例 | `ari_worker_jobs_total{result="completed"}` / 总数 | `/metrics` |
| 6 | 单次运行成本 | 一次分析花多少钱 | `SELECT SUM(estimated_cost_usd) FROM model_usage WHERE run_id = ?` | `model_usage` 表 |

第 6 项刻意**没有**做成指标：成本是"每次运行结束时算一次"的量，做成随时间变化的曲线会
诱导人盯着一张没有信息量的图。要看成本就查库或看运行面板。

**第 1 项只覆盖 worker，这是有意的**：Streamlit 的脚本按会话执行，没人打开页面时 web 进程里
根本没有 `/metrics` 端点（D-14）。给它设一个永远 down 的抓取目标，换来的是常态误报。
web 的存活由容器健康检查覆盖（Streamlit 自带的 `/_stcore/health`）——那是探针该管的事，
不是时间序列该管的事。

## SLO 目标

| # | 目标 | 值 | 依据 |
|---|---|---|---|
| 1 | 可用性 | ≥ 99%（每 30 天允许约 7 小时） | 单机自托管：允许计划内重启与部署窗口 |
| 2 | 就绪 | 就绪状态在部署完成后 5 分钟内恢复 | 调度器启动是同步的，超过 5 分钟一定是出了问题 |
| 3 | 阶段 P95 | 每阶段 ≤ 120 秒 | 初始值。当前最高频的阶段是 `analyze_batches`（含模型调用） |
| 4 | 模型调用 P95 | ≤ 60 秒 | 与 `MODEL_TIMEOUT_SECONDS=60` 对齐：超过它，重试会开始频繁发生 |
| 5 | 任务成功率 | ≥ 95% | 初始值。失败应主要来自上游接口波动，而不是自身缺陷 |
| 6 | 单次运行成本 | ≤ $0.10 | 依据实测：30 用例评测 $0.075；一次完整分析（20 条样例、13 次调用）$0.0196 |

**第 3、4 项的措辞是有意的**：写"P95 ≤ 120 秒"而不是"平均 ≤ 120 秒"。平均值会把少数
特别慢的运行抹平，而那恰恰是用户会抱怨的部分。

## 错误预算与处置

错误预算 = 1 − SLO。以可用性 99% 为例，30 天约 7.2 小时。

| 预算消耗 | 处置 |
|---|---|
| < 50% | 正常迭代：照常合并功能 |
| 50% – 100% | 只修问题不加功能；新增功能需要说明为什么不会进一步消耗预算 |
| 已耗尽 | 冻结功能变更，先修稳定性；直到连续 7 天没有新的消耗 |

预算**按周看趋势**，不看单点：一次 3 分钟的部署重启不该触发任何动作。

## 怎么验证这些数字是真的

```powershell
# 起栈（含 Prometheus 与 Grafana）
docker compose --profile observability up -d

# 直接看原始指标
curl -s http://localhost:9100/metrics | Select-String 'ari_stage_duration'   # 阶段耗时（含 web 进程跑出来的）
curl -s http://localhost:9100/metrics | Select-String 'ari_worker'          # 进程与任务

# 看板：http://localhost:3000（匿名只读，无需登录）
# 告警规则：http://localhost:9090/alerts
```

规则文件本身的正确性由测试守着（`tests/test_ops_assets.py`）：**告警里引用的每个指标都必须
真实存在于 `/metrics` 输出**——引用不存在的指标等于一条永远不会触发的假告警。

## 现在还没做到的

- 没有长期存储：单机 Prometheus 保留 15 天，跨月对比需要外部存储。
- 没有真实流量基线：上表里的「初始值」来自样例与评测运行，不是生产分布。
- 没有多实例：可用性 SLI 只在**单进程**意义上有定义，横向扩容后要改成按实例聚合。
